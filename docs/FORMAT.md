# Формат хранения ZaPassKa

Документ описывает всё, что нужно второй реализации, чтобы открыть то же
хранилище: параметры криптографии, раскладку блобов, структуру снимка и
правила слияния. Эталонные значения лежат в
[`format/vectors.json`](format/vectors.json), и любая реализация обязана
проходить их.

Версия формата снимка: **1**.

---

## 1. Криптография

| Параметр | Значение |
|---|---|
| Вывод ключа | scrypt, `N = 2^17`, `r = 8`, `p = 1`, длина 32 байта |
| Шифрование | AES-256-GCM |
| Nonce | 12 байт, случайный для каждой операции |
| Тег | 16 байт |
| Дополнительные данные (AAD) | не используются |

Любой зашифрованный блоб имеет вид:

```
nonce (12 байт) || ciphertext || tag (16 байт)
```

Тег GCM всегда идёт в конце шифротекста, как его добавляют стандартные
реализации. Отдельно он нигде не хранится.

Соль scrypt имеет длину 32 байта и хранится в шестнадцатеричном виде.

Параметры scrypt менять нельзя: они входят в формат. Их изменение сделает
существующие хранилища нечитаемыми.

---

## 2. Иерархия ключей

У каждого хранилища есть случайный **ключ данных** длиной 32 байта. Им и
только им шифруются поля записей.

Способ входа выводит из своего секрета **ключ-обёртку** и хранит ключ данных,
зашифрованный этой обёрткой:

```
секрет + соль ──scrypt──► ключ-обёртка ──AES-GCM──► wrapped_dek
                                                        │
                                          ключ данных ◄──┘
                                                        │
                                              поля записей
```

Проверка секрета отдельной сущностью не нужна: если обёртка не
распаковывается, GCM возвращает ошибку аутентификации, и это и означает
неверный секрет.

Хранилище имеет **ровно один** действующий способ входа. Смена способа или
смена пароля это перезапись `wrapped_dek`; записи при этом не трогаются.

---

## 3. Способы входа

| Поле | Тип | Описание |
|---|---|---|
| `method` | строка | `master` или `ad` |
| `identity` | строка | для `ad` это `sha256(логин в нижнем регистре)` в hex, для `master` пустая строка |
| `salt` | hex | соль scrypt |
| `wrapped_dek` | base64 | ключ данных под ключом-обёрткой |
| `updated_at` | строка | отметка времени, см. раздел 5 |
| `deleted` | 0 или 1 | надгробие вместо удаления |

Ключ записи это пара `(method, identity)`.

Мобильные клиенты, как правило, поддерживают только `master`: до контроллера
домена с телефона обычно не достучаться.

---

## 4. Снимок

Снимок это всё хранилище одним документом JSON в кодировке UTF-8.

```jsonc
{
  "format": 1,
  "vault_id": "uuid",
  "updated_at": "2026-02-03T11:30:00.000000Z",
  "unlock_methods": [ { /* раздел 3 */ } ],
  "entries": [
    {
      "uuid": "uuid",
      "service":  "base64 блоба",
      "login":    "base64 блоба",
      "password": "base64 блоба",
      "updated_at": "2026-02-01T10:00:00.000000Z",
      "deleted": 0
    }
  ]
}
```

Правила чтения:

- `format` больше поддерживаемого означает отказ читать снимок, а не попытку
  разобрать его частично;
- у надгробия (`deleted = 1`) поля пустые, расшифровывать их не нужно;
- незнакомые поля сохраняются при перезаписи, если реализация умеет, и
  игнорируются в остальном.

Всё содержимое снимка либо открыто и безопасно (соли, отметки времени,
идентификаторы), либо зашифровано. Ключ данных в снимок не попадает никогда.

---

## 5. Отметки времени

Формат строгий: `%Y-%m-%dT%H:%M:%S.%fZ`, всегда UTC, микросекунды
обязательны. Строки сравниваются лексикографически, поэтому строковое
сравнение эквивалентно сравнению моментов времени. Реализация не должна
разбирать их в тип даты для сравнения.

---

## 6. Слияние

Синхронизация это цикл: скачать снимок, слить с локальными данными,
выгрузить результат.

1. **Записи** сопоставляются по `uuid`, **способы входа** по паре
   `(method, identity)`.
2. Побеждает запись с более поздним `updated_at`. При равенстве остаётся
   локальная.
3. Удаление это надгробие, оно участвует в сравнении наравне с обычной
   записью, поэтому удалённое на одной машине не воскресает с другой.
4. Надгробия старше 90 дней удаляются.
5. После слияния у хранилища должен остаться один действующий способ входа.
   Если их несколько, оставляется самый поздний по `updated_at`; при равенстве
   порядок определяется парой `(method, identity)`. Выбор обязан быть
   одинаковым на всех машинах.
6. Если одним секретом открываются несколько хранилищ, они объединяются.
   Выживает хранилище с **наименьшим** `vault_id` при обычном строковом
   сравнении. Записи переносятся в него, затем гасятся надгробиями в исходном.
   Идентификатор перенесённой записи вычисляется как
   `uuid5(namespace = vault_id выжившего, name = прежний uuid записи)`, иначе
   две машины создадут разные идентификаторы и запись покажется дважды.

---

## 7. Хранение в Google Диске

| Что | Значение |
|---|---|
| Scope | `https://www.googleapis.com/auth/drive.appdata` |
| Папка | `appDataFolder` |
| Имя файла | `zapasska-<vault_id>.json` |
| Содержимое | снимок из раздела 4 |

Один файл на хранилище. Поиск идёт по имени файла в пределах
`appDataFolder`; другие файлы в этой папке игнорируются.

Вход в аккаунт выполняется браузером, потоком authorization code с PKCE.
Клиентские идентификаторы у платформ разные, но папка и scope общие, поэтому
данные видны всем клиентам одного пользователя.

## 8. Локальное хранилище

Схема SQLite десктопного клиента приведена в
[ARCHITECTURE.md](ARCHITECTURE.md). Другая реализация не обязана повторять её:
обязателен только формат снимка. На практике повторить удобно, потому что
правила слияния оперируют теми же полями.

---

## 9. Эталонные векторы

[`format/vectors.json`](format/vectors.json) содержит:

- вывод ключа scrypt для двух паролей с фиксированными солями;
- ключ данных, завёрнутый под известным ключом-обёрткой;
- зашифрованные поля, включая строку с кириллицей и эмодзи;
- целый снимок с мастер-паролем, ожидаемым ключом данных, ожидаемыми
  записями и одним надгробием.

Новая реализация считается совместимой, когда воспроизводит все эти значения.
Файл генерируется скриптом `tools/make_vectors.py` и проверяется тестами
`tests/test_format_vectors.py`.

Векторы нельзя перегенерировать ради того, чтобы упавший тест позеленел:
падение означает, что изменение ломает совместимость со всеми уже
существующими хранилищами.

---

## 10. Изменение формата

- Обратно совместимые добавления: новые необязательные поля, которые старый
  клиент игнорирует. Номер версии не меняется.
- Несовместимые изменения: увеличение `format`. Старый клиент обязан
  отказаться читать такой снимок и сообщить пользователю, что нужна новая
  версия.
- Параметры scrypt и раскладка блоба несовместимы по определению: их
  изменение требует перешифрования всех хранилищ и здесь не предусмотрено.
