# 🔐 ZaPassKa

Менеджер паролей с двумя способами входа — через Active Directory или по
мастер-паролю — и двусторонней синхронизацией через Google Диск.

## Стек

- **UI**: PyQt6
- **БД**: SQLite (`%APPDATA%\ZaPassKa\tp.sec`, на Linux `~/.zapasska/tp.sec`)
- **Шифрование**: AES-256-GCM, ключ данных обёрнут ключом из scrypt
- **Аутентификация**: LDAP через `ldap3` либо локальный мастер-пароль
- **Облако**: Google Drive `appDataFolder`, OAuth 2.0 без сторонних библиотек

## Как устроено шифрование

У каждого хранилища есть случайный 256-битный **ключ данных**. Только им
шифруются записи. Каждый способ входа выводит свой **ключ-обёртку** через
scrypt и хранит копию ключа данных, зашифрованную этой обёрткой.

```
AD-пароль    ──scrypt(соль_ad)──►  ключ-обёртка ──► wrap(ключ данных)
мастер-пароль ──scrypt(соль_mp)──►  ключ-обёртка ──► wrap(ключ данных)
                                                          │
                                           записи ◄───────┘  AES-256-GCM
```

Параметры scrypt: `N=2^17, r=8, p=1` — около секунды и 128 МБ памяти на одну
попытку подбора.

Что из этого следует:

- Оба способа открывают **одни и те же записи**.
- Переход с AD на мастер-пароль и обратно — это перезапись одной обёртки.
  Записи не перешифровываются, потерять их в процессе невозможно.
- Смена пароля в домене тоже решается перезаписью обёртки, а не
  перешифрованием всей базы.
- Неудачная распаковка обёртки (`InvalidTag`) сама по себе означает неверный
  секрет, поэтому ни пароль, ни отдельный верификатор нигде не хранятся.

Формат любого блоба: `nonce(12) + ciphertext + tag(16)`, nonce случайный для
каждого поля.

## Способы входа

Переключатель **Unlock with** в окне входа выбирает режим, выбор запоминается
в QSettings (реестр на Windows, ini-файл на Linux и macOS).

| Режим | Что происходит |
|---|---|
| **Active Directory** | Пароль проверяется на контроллере домена, затем распаковывает ключ данных |
| **Master password** | Домен не участвует, ключ данных распаковывается паролем, который знает только пользователь |

У хранилища всегда **ровно один** активный способ входа. Двух одновременно не
бывает: включение одного выключает другой.

### Переход между режимами

Переключить способ можно только у **открытого** хранилища, иначе ключа данных
в памяти нет и обернуть его нечем. Порядок такой:

1. Войдите текущим способом.
2. В окне хранилища откройте **🛡 Security**. Там видно, чем хранилище
   открывается сейчас.
3. Нажмите **Switch to a master password…** или **Switch to Active
   Directory…**. Во втором случае пароль сначала проверяется на контроллере
   домена.

Переключение переписывает обёртку ключа и гасит старую. Новая обёртка
записывается раньше, чем удаляется старая, поэтому сбой посреди операции
оставит хранилище открываемым, а не запертым. Записи при этом не трогаются.

Кнопка **Create a vault with a master password** в окне входа создаёт новое
**пустое** хранилище. Она нужна тем, у кого домена нет вообще; чтобы перевести
на мастер-пароль уже существующие записи, используйте раздел Security.

### Смена пароля в домене

AD принял пароль, но обёртка им не распаковывается, значит пароль в домене
сменился. Приложение один раз спросит предыдущий пароль и перезапишет обёртку
новым. Записи при этом не трогаются.

Если предыдущий пароль забыт, хранилище останется зашифрованным: ключ обёрнут
прежним паролем, и распаковать его больше нечем. Запасного пути нет, потому
что активный способ входа только один. Это плата за требование «два
одновременно нельзя», и об этом стоит предупреждать пользователей при
внедрении.

## Синхронизация с Google Диском

### Что и куда сохраняется

Одно хранилище — один JSON-файл в `appDataFolder`: скрытой папке Диска,
доступной только этому приложению. Запрашивается единственный scope
`drive.appdata`, к документам пользователя доступа нет.

В файле лежат обёрнутые ключи, соли и зашифрованные поля записей. Ключ данных
и пароли за пределы машины не выходят; тест
`test_snapshot_carries_no_plaintext` проверяет, что в снимке нет открытого
текста.

### Когда запускается

- при открытии хранилища;
- после каждого добавления, изменения и удаления записи;
- после изменений в разделе Security;
- вручную кнопкой **☁ Sync**.

Запись сначала попадает в локальную базу и только потом уходит в облако,
поэтому отсутствие сети её не теряет. Неудачная синхронизация не роняет
приложение: сбой показывается в строке состояния, а накопленные изменения
уезжают при следующей удачной синхронизации.

### Как сливаются изменения

Двусторонний цикл: скачать снимок → слить с локальной базой → выгрузить
результат. Слияние идёт по отдельным записям, а не по файлу целиком:

- ключ записи это её `uuid`, ключ способа входа это пара `(method, identity)`;
- побеждает запись с более поздним `updated_at`, при равенстве остаётся
  локальная;
- удаление едет как «надгробие» (`deleted=1`), поэтому удалённая на одном ПК
  запись не воскресает с другого;
- надгробия старше 90 дней вычищаются;
- если два ПК переключили способ входа порознь, после слияния остаётся один,
  более поздний по `updated_at`, и обе машины приходят к одному и тому же.

### Второй компьютер

На новой машине нажмите **☁ Google Drive backup…** в окне входа и подключите
тот же аккаунт. Приложение скачает снимки, и дальше вход выполняется как
обычно — тем же мастер-паролем или той же доменной учёткой. Если Диск уже
подключён, снимки подтягиваются автоматически при запуске.

### OAuth-клиент

Пользователь входит в свой аккаунт Google в браузере, приложение получает
только код авторизации. Пароль от Google приложение не видит.

Официальные сборки несут клиент, подставленный из секретов репозитория
(`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`). Если сборка собрана без них,
приложение попросит свой клиент: в Google Cloud Console включите Drive API,
создайте OAuth-клиент типа **Desktop app** и вставьте его ID и secret в
диалоге Google Drive. Также читаются переменные окружения
`ZAPASSKA_GOOGLE_CLIENT_ID` и `ZAPASSKA_GOOGLE_CLIENT_SECRET`.

Refresh-токен лежит в `google_token.json` рядом с базой, с правами `600` там,
где ОС их поддерживает. Кнопка **Disconnect** отзывает его у Google.

## Схема БД

```sql
-- Хранилище: набор записей с общим ключом данных
CREATE TABLE vaults (
    id         TEXT PRIMARY KEY,
    created_at TEXT NOT NULL
);

-- Способы открыть хранилище
CREATE TABLE unlock_methods (
    vault_id    TEXT NOT NULL,
    method      TEXT NOT NULL,          -- 'ad' | 'master'
    identity    TEXT NOT NULL,          -- sha256(логин) для AD, '' для мастер-пароля
    salt        TEXT NOT NULL,          -- соль scrypt, hex
    wrapped_dek BLOB NOT NULL,          -- ключ данных под ключом-обёрткой
    updated_at  TEXT NOT NULL,
    deleted     INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (vault_id, method, identity)
);

-- Записи: всё зашифровано ключом данных
CREATE TABLE entries (
    uuid       TEXT PRIMARY KEY,
    vault_id   TEXT NOT NULL,
    service    BLOB NOT NULL,
    login      BLOB NOT NULL,
    password   BLOB NOT NULL,
    updated_at TEXT NOT NULL,
    deleted    INTEGER NOT NULL DEFAULT 0
);
```

### Миграция старой базы

База прошлой версии (`kdf_salts` + `passwords`, шифрование напрямую
AD-паролем) конвертируется при первом входе пользователя: записи
расшифровываются старым ключом, перекладываются в новое хранилище со
случайным ключом данных, старые строки удаляются. Переносятся только те
строки, которые расшифровались ключом этого пользователя, поэтому несколько
человек на одной машине мигрируют независимо. Когда мигрируют все, старые
таблицы удаляются.

## Главное окно

- Таблица: Сервис / Логин / Пароль (скрыт `••••••••••••`)
- **👁 Show** — показать или скрыть пароль в строке; открытым может быть
  только один пароль, показ следующего прячет предыдущий
- **📋 Copy** — скопировать пароль; через 30 секунд буфер очищается, но только
  если в нём всё ещё лежит этот пароль
- **✎ Edit** — изменить запись
- **🗑** — удалить с подтверждением
- **＋ Add Entry** — новая запись, есть генератор на 16 символов
- **Поиск** — фильтр по сервису и логину
- **☁ Sync** — синхронизация вручную
- **🛡 Security** — способы входа в хранилище
- **📌 On Top** — окно поверх остальных, выбор запоминается между запусками
- **Sign out** — выход, ключ данных стирается из памяти

## Значок приложения

`icon.ico` встраивается в `.exe` как ресурс, и в проводнике Windows файл сразу
с картинкой. У исполняемого файла Linux такого места нет вообще, поэтому
значок задаётся уже на старте через Qt: обе картинки едут внутри сборки, а
`main.py` ставит их приложению. Этого хватает, чтобы окно и панель задач
показали нужный значок на обеих системах.

Для полноценного пункта в меню приложений Linux нужен ещё файл `.desktop`.
Скачайте бинарник, положите рядом `icon.png` и `packaging/ZaPassKa.desktop`,
затем выполните:

```bash
./packaging/install-linux.sh
```

Скрипт разложит файлы по `~/.local`, подставит реальный путь к бинарнику и
попросит панель перечитать список приложений. Значок в закреплённом ярлыке
подхватится по имени `zapasska` из темы hicolor.

## Тесты

```bash
python -m unittest discover -s tests -v
```

| Файл | Что проверяет |
|---|---|
| `tests/test_crypto.py` | обёртки ключа, переход между способами входа, смена пароля в домене, миграция старой базы |
| `tests/test_sync.py` | слияние снимков на двух машинах: правки, удаления, способы входа, отсутствие открытого текста |
| `tests/test_cloud_sync.py` | поведение без сети: запись переживает сбой и уходит следующей синхронизацией |
| `tests/test_ui_smoke.py` | окна собираются и отрисовывают записи, показ паролей, запоминание режима окна, загрузка значка; пропускается, если Qt недоступен |

Тесты подменяют путь к БД через `ZAPASSKA_DB` и снижают параметры scrypt,
поэтому идут меньше секунды.

## Сборка

Workflow `.github/workflows/build.yml` на каждый push:

1. **Tests** — прогон тестов на ubuntu-latest;
2. **Build** — PyInstaller на windows-latest и ubuntu-latest, по одному
   самодостаточному файлу на платформу, результат в артефактах
   `ZaPassKa-windows-x64` и `ZaPassKa-linux-x64`;
3. **Publish release** — на тег вида `v1.2.3` создаётся релиз с обоими
   файлами.

Локально то же самое:

```bash
pip install pyinstaller
pyinstaller --noconfirm --clean main.spec
```

## Безопасность

- ✅ Ни AD-пароль, ни мастер-пароль нигде не сохраняются
- ✅ Записи шифруются ключом данных, который никогда не покидает память
- ✅ AES-256-GCM — аутентифицированное шифрование, подмена данных заметна
- ✅ scrypt с высокими параметрами защищает обёртку от перебора
- ✅ В Google Диск уходит только шифротекст, scope ограничен `drive.appdata`
- ⚠️  Мастер-пароль восстановить нельзя: забыт — хранилище не открыть
- ⚠️  Сертификат контроллера домена не проверяется (`CERT_OPTIONAL`) —
  осознанное решение для доменов с самоподписанными сертификатами
- ⚠️  Refresh-токен Google хранится в файле, защищён только правами доступа
- ⚠️  При одновременной правке одной записи на двух ПК выигрывает та, что
  сохранена позже
